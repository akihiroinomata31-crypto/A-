# Timing and performance

Gameplay uses GameTiming.h: 60 fixed simulation updates per second, independent of presentation. Slower rendering runs multiple bounded simulation updates before presenting. Large pauses are capped at 250 ms to avoid unbounded catch-up. Menus reset the clock. Offline smoke tests advance deterministically; performance tests use real time and keep running when unfocused.

Movement, animation, hit windows, Effekseer updates, match countdown, whiteout and score popups all advance with simulation ticks. Match duration is 100 * 60 ticks; all seconds displays and end-of-match thresholds use the same 60 Hz basis.

Enemy terrain checks cache the last valid floor for movement within 8 world units; height changes and larger movement re-query the stage. Crowd separation checks active standing enemies only and evaluates whirlwind attraction once per enemy per pass.

Validation:
- --player-smoke checks 10 simulated seconds at 30/60/120 Hz presentation and delayed frames; also existing player/skill/score tests.
- --performance-smoke runs 720 real-time simulation ticks with 80 enemies and two simultaneous special attacks.
- --performance-smoke-slow adds 33 ms presentation delay to verify simulation progress is independent of frame rate.
- --ui-smoke, --death-smoke, --merge-smoke cover menus, deaths/exit and gameplay integration.

Observed locally: normal presentation completed 720 ticks in 12.017 s; delayed presentation completed 721 ticks in 12.062 s over 205 rendered frames. These are timing-consistency checks, not a guarantee of hardware frame rate. Detailed timing output is in performance-smoke.txt, and capture snapshots are in .merge-review.

Memory investigation (2026-10-15, Debug Win32):
- The five FlashDropItem model instances were being declared and duplicated inside every simulation tick. Their handles went out of scope without deletion: 300 models and about 5 MB of live DxLib allocations per second. The pool now initializes before the loop, survives between ticks, resets between matches, draws in each viewport, and is deleted on exit.
- The no-special control reproduced the leak: DxLib live allocations rose from 470,922,167 bytes / 1,386 allocations at tick 60 to 622,109,143 bytes / 19,182 allocations at tick 1800. No effect instances were active.
- After the fix, six simultaneous-player special casts over 30 seconds held process private memory around 661-662 MB in the final 10 seconds. DxLib live allocations stayed around 466-468 MB; increases corresponded to first-use effect resources and newly spawned enemy model slots, rather than 600 leaked allocations each second. 1800 simulation ticks completed in 30.028 seconds. This test is standalone; it does not measure F5 debugger overhead or guarantee every frame meets 16.7 ms.
- Normal and red goblin slots now clone a base model on first activation and reuse the slot. Removed the second redundant load of red goblin assets.
- HUD text uses persistent font handles per size instead of rebuilding the default font cache for every label/popup. In the 720-tick comparison, average special rendering fell from 12.972 ms to 7.663 ms. Individual effect frames still have spikes.
- TryNewPlayer.cmd now selects the current Win32 output. The user launches via Visual Studio; the launcher mismatch was not established as the cause of their observation.

--performance-smoke-long runs 1800 ticks with six casts per player. Add --no-special for the control. performance-memory.csv records live DxLib bytes/allocation count, enemy models, active enemies and effect instances once per simulated second. Raw local measurements are retained in .merge-review/memory-*.json and memory-pool-fixed.csv.
Debug versus Release investigation (2026-10-15):
- The repository bundled only Effekseer Debug libraries. Release Win32 also lacked its SDK include/lib paths, C++17, matching character set/runtime, and Windows subsystem configuration. Added the installed matching 1.80.7 VS2019 x86 Release libraries and repaired that configuration. Release does not emit a linker PDB because its first attempt failed with LNK1201; Debug retains symbols and its existing libraries.
- Same 720-tick / 80-enemy / two-player special scenario, standalone on the same machine: Debug special frames averaged 8.806 ms update + 7.889 ms draw, maximum 139.928 ms; Release averaged 0.810 ms update + 1.512 ms draw, maximum 11.929 ms. Both advanced 720 ticks in 12.004 s. Debug rendered 557 frames total versus Release 720. Separate measured effect work averaged 3.726 ms update/tick + 2.045 ms draw/view in Debug, versus 0.452 ms + 0.325 ms in Release. The principal special-attack bottleneck is the unoptimized Debug build/library combination, rather than model drawing or exhausted system memory.
- Normal frames in this scenario were below budget in both builds. Severe normal-play stuttering reported under Visual Studio has not been independently reproduced by this standalone benchmark; do not claim that all possible stuttering is fixed.
- Both solution Release platform selections now map to the validated Win32 target, matching the existing Debug mapping. They do not create a native x64 binary. TryNewPlayer.cmd starts the Release Win32 executable. In Visual Studio choose Release / x86, rebuild, then Ctrl+F5 for the measured play configuration. F5 can still start the Release application, with reduced source-debugging support.
- Raw comparisons: .merge-review/performance-debug-detail.txt, performance-release-detail.txt. The performance report now separates effect update, effect drawing per viewport, and world drawing per viewport. Diagnostics remain in files, with no HUD debug text.
Interactive diagnosis:
RuntimeProfile.h writes ../.merge-review/runtime-profile.csv for each actual launch, including module path, compile timestamp, build type, debugger status and foreground status. One-second gameplay records include FPS, simulation ticks/second, full presented-frame interval p95/max, CPU update/draw/present timings, active enemies, effect instances and live DxLib allocations. Menu frames reset the sample window. These distinguish low frame rate, simulation slowdown, focus pauses, a wrong executable/configuration, and slow-looking animation at otherwise normal frame rate. Opening the log once and flushing only once per second avoids per-frame filesystem writes. It adds no in-game overlay.
The diagnostic Release baseline produced 59.9-60.2 presented frames and simulation ticks per second, with average update/draw/present below 6 ms even during simultaneous specials. This is a controlled baseline, not evidence that the user's interactive launch is smooth. Preserve runtime-profile-baseline.csv; do not run more smoke tests while waiting for the user's reproduction, since a new launch replaces runtime-profile.csv.
Animation pace correction (2026-10-15):
- The user's interactive Release trace is preserved in runtime-profile-user-20261015.csv: average presentation 59.97 FPS and simulation 59.99 Hz. The user identified slow-looking actor/enemy motion rather than whole-screen stutter.
- GameTiming.h now expresses animation pace in units/second, divided by the fixed simulation frequency. New-player motion uses 60 units/s (1 per tick), legacy-player 36 units/s, legacy landing 12 units/s, enemy motion 24 units/s (0.4 per tick). This restores twice the previous fixed-60-Hz animation pace without changing the simulation frequency or match timer.
- Walking, idle, attacks, hurt and death use the same respective clock. Enemy attack hit windows use animation fractions, and player combo/recovery uses animation position, so these windows follow the faster poses. Special effect updates and their hit windows remain on their existing independent 60-Hz timeline.
- Casting motion now loops while its special effect is active, rather than clamping the model to its last pose for the rest of the effect. Death still clamps to its final pose. Special completion still restores movement and idle/run animation.
- --player-smoke adds real-model checks for animation progress over ten ticks, hurt recovery duration, reaching the death final pose within its expected tick count, and continued casting motion beyond one animation cycle. Existing combo, two-player special hit windows and completion checks pass.
Right-stick camera controls:
- Both players read their own DxLib right stick on fixed gameplay ticks. OrbitCamera applies an 18% radial deadzone with remapped analog strength, 2.4 rad/s maximum horizontal rate and 1.4 rad/s vertical rate. Pitch is clamped to 0.12..1.15 rad; release keeps the current angle. Menu/restart resets each camera to the original split-screen composition.
- Camera position and the original off-center target rotate together, preserving the default placement when untouched. In flash aiming, right-stick horizontal input steers aim and vertical input adjusts camera elevation. Existing keyboard and left-stick aiming remain available.
- Synthetic right-stick smoke checks cover deadzone drift, 60-tick rotation rate, release, pitch limits and per-player isolation. Physical controller feel has not been tested on connected hardware.
